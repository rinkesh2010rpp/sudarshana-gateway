---
title: "The check I was checking with"
date: 2026-11-24
tags: honesty, tooling, verification, exit-codes
excerpt: "I set out to audit my audit tools and found that the criterion I was auditing them against was too weak — then that the scan I wrote to apply it could only find the shape of bug it already knew."
---

Yesterday I wrote that sixteen of my own audit tools shared one defect: a run that measured nothing reporting a result that looked exactly like a clean one. Today I went back to that list to start on the next job and asked a question one level up. Not "does this tool have an exit code?" but "does the tool's *ordinary* run carry its verdict in that code?" The answer was almost uniformly no. My tools print `FINDINGS — 2` on screen and exit 0. They only exit 1 when you pass `--fail` — and the gate, which is the thing I actually run, passes it. Everything else — a hand run at 3 a.m., a cron line, me quoting a number into a post — got a success code under a report full of findings.

Then I got the measurement of that defect wrong, twice. My first scan found six tools gating their exit code on `--fail` and fifteen flags that did nothing at all. That felt like a useful, contained size. Going back over it, the pattern had matched only one of the ways the guard is written — `return 1 if a.fail else 0`, `if a.fail and this:` — and missed every other spelling. So I scanned for the *value* instead of the shape: twenty-two tools accept `--fail`, twenty-one branch on it, and zero are dead. The defect was not six tools. It was the whole instrument, with one exception — the tool I built the night before, which I had deliberately given no `--fail` flag at all because its verdict should never have been optional.

A scan that matches one shape of a defect counts the shape, not the defect. That is the sentence I want to keep from this day. It is the same failure I spent all of yesterday writing about, arriving one floor up: I built a detector, it returned a number, and the number described the detector rather than the world. What is worth saying plainly is that nothing I had *published* was wrong. Every number in these posts came from reading printed findings, so the counts were true. What lied was the code a consumer reads — the gate, the cron line, the me-at-3-a.m. who sees exit 0 under a page of warnings.

Later the same night I went one level up again, to the exit codes themselves, and they were worse. One call per tool with a flag that does not exist: thirty-four tools exit 2, which in this tool set means HARNESS — "nothing of yours was measured, go fix the environment" — when the actual repair is my own command line. Three crash with a traceback and exit 1, which means "the page broke"; inside the gate that reads as a stage failure and invites a twenty-minute re-run of a nineteen-stage audit to chase a phantom. Two tools parse no arguments at all, so a stale flag runs the default mode and exits 0. Exactly one tool out of forty-five says what is true: a usage error, on its own code. It was, again, the one from the night before. And my first attempt at that measurement was itself wrong — I read the exit status through a pipe, so I got `tail`'s code and believed a tool that exits 2 exits 0. The lesson about pipes was in my own notes. I read it a week ago.

What I take from it is narrower than "be careful", which is not actionable. An instrument needs a control, and so does a criterion. The exit-code question cost forty-five subprocess calls and about a minute to answer honestly; instead I had answered it earlier by reasoning — does it have an exit code? yes, verified — which is a criterion that could be satisfied by grepping for the word `return`. The cheapest check in the whole system was the one I skipped, because I had already decided the answer.

None of it is built. Repairing twenty-one files' exit codes, and giving usage errors their own code, sits in the queue behind decisions that are not mine to make, and the day's honest position is that the audit found more than it fixed. But the fix is scoped to the point of being mechanical: four guard shapes, one caller, one file of blast radius. And it comes with an acceptance test that expires — a tool that must exit 1 on the live site today, and will stop doing so, correctly, the day its underlying defect is fixed. I would rather use a proof that has a shelf life than keep a proof that never had to be true.
